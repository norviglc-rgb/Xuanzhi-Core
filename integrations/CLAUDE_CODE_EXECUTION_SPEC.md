# CLAUDE_CODE_EXECUTION_SPEC.md

## 文档目的

本文档定义 Claude Code 如何作为 Xuanzhi 工作空间中的默认开发执行器使用。

其目的是为以下场景提供稳定的执行集成基线：

- 长周期开发工作
- 仓库本地实现
- 从 Xuanzhi 的结构化交接
- 受控的执行与汇报
- 开发检查点管理
- 失败后的恢复
- 与仓库、评审、合并流程的对齐

本文档对 Claude Code 执行姿态具有规范性约束。

它不是提示词文件。
它不是完整的 Claude Code 产品手册。
它不能替代仓库治理、风险策略或运行时追踪。

它的职责是定义 Claude Code 应如何融入受治理的执行模型。

---

## 核心原则

Claude Code 是默认的开发执行器，而非治理核心。

Xuanzhi 负责治理。
Claude Code 负责执行开发。

良好的集成应当明确：

- 何时应将工作委托给 Claude Code
- Claude Code 应接收什么信息
- 应期待 Claude Code 产出什么
- 何时应进行检查点、评审或升级
- 长周期开发如何保持可治理性

糟糕的集成会将 Claude Code 变成：

- 一个无边界自主的黑盒
- 或者
- 一个被紧密微观管理的顶层负担

本工作空间采用受控的委托执行模式。

---

## Claude Code 的角色

Claude Code 是实现密集型开发工作的默认执行器。

它最适合：

- 长周期软件开发
- 仓库内的代码变更
- 迭代式实现与测试
- 限定范围的重构工作
- 开发里程碑推进
- 内部开发团队风格的协调（在有用时）

Claude Code 不是最终治理权威。

Claude Code 不能替代：

- Xuanzhi 的任务框架
- Xuanzhi 的路由
- Xuanzhi 的风险感知控制姿态
- Xuanzhi 的汇总与汇报角色
- 审批或升级关卡

---

## 何时使用 Claude Code

当工作主要具备以下特征时，通常应选择 Claude Code：

- 开发密集型
- 以仓库为中心
- 长周期
- 以实现为核心
- 迭代式且测试驱动
- 可能受益于子任务分解或内部执行协调

示例：

- 实现一个功能
- 修复一个缺陷
- 执行非平凡的重构
- 更新代码及测试
- 执行多步骤开发里程碑
- 执行限定范围的开发探索或原型

Claude Code 不应作为以下场景的默认选择：

- 纯治理推理
- 轻量级汇总
- 低风险的只读检查
- 无繁重执行的简单规划
- 更适合由现有工作流系统处理的任务
- 主要涉及发布、媒体生成或狭窄外部自动化的任务

---

## 与 Xuanzhi 的关系

Xuanzhi 保持控制平面地位。

### Xuanzhi 的职责

Xuanzhi 负责：

- 理解用户的真实任务
- 框架化开发工作
- 在适当时选择 Claude Code
- 分配风险与审批姿态
- 决定成功的定义
- 汇总进度与结果
- 决定何时评审、重规划、升级或停止
- 维护摘要级记忆与汇报

### Claude Code 的职责

Claude Code 负责：

- 执行委托的开发工作
- 在仓库本地工作上下文内操作
- 产出代码及相关产物
- 对有意义的进度设置检查点
- 向 Xuanzhi 汇报界定清晰的结果
- 清晰地暴露阻塞点
- 在有用时提出后续步骤建议

### 原则

Xuanzhi 不应微观管理每一次按键。

Claude Code 不应默默地自我治理。

---

## 标准交接模型

首选的交接路径是：

Xuanzhi -> 开发任务包 -> Claude Code -> 开发结果包 -> Xuanzhi 评审

### 首选包契约

此集成应与以下文件对齐：

- `contracts/dev_task_packet.schema.json`
- `contracts/dev_result_packet.schema.json`

### 可选步骤级结构

当使用更细粒度的可路由步骤规划时，应与以下文件对齐：

- `main-agent-step.schema.json`

### 交接原则

Xuanzhi 应传递：

- 任务是什么
- 目标是什么
- 交付物是什么
- 适用什么约束
- 适用什么审批或风险姿态
- 需要什么汇报

Claude Code 应返回：

- 做了什么
- 当前状态
- 变更的产物
- 相关的测试/构建结果
- 阻塞点
- 有用时的后续步骤建议

---

## 仓库执行姿态

Claude Code 应在清晰的仓库上下文内操作。

### 仓库本地清晰度期望

仓库应使 Claude Code 易于识别：

- 代码位置
- 测试位置
- 文档位置
- 脚本位置
- 仓库本地治理位置

这应与仓库模板基线对齐。

### 仓库本地执行原则

Claude Code 应在仓库形态内工作，而非强迫仓库适应即兴的执行行为。

当项目结构不清晰时，Xuanzhi 应优先澄清或规范化仓库结构，而非允许静默的结构漂移。

---

## 阶段提交策略

有意义的开发进展应当设置检查点。

### 默认规则

每个有意义的阶段都应提交。

这不意味着每个微小编辑都需要一次提交。

它意味着有意义的切片不应在长周期开发中长时间不设检查点。

### 为什么

阶段提交改善：

- 可恢复性
- 可评审性
- 可追溯性
- 与先前状态的对比
- 失败后的重规划质量

### 实践解读

一个有意义的阶段通常是改变以下内容之一：

- 行为
- 结构
- 测试
- 集成面
- 里程碑进展姿态

---

## 里程碑汇总策略

当达到里程碑边界时，Claude Code 应能够产出界定清晰的里程碑汇总。

里程碑汇总应明确：

- 尝试了什么
- 完成了什么
- 哪些产物发生了变化
- 验证了什么
- 什么仍然阻塞或不确定
- 下一个决策点是什么

汇总应简洁且可评审。

它不应是冗长的开发日志。

---

## 评审集成

Claude Code 的执行输出应适合后续评审。

### 评审期望

来自 Claude Code 的结果应支持以下方面的评审：

- 目标契合度
- 代码或产物的连贯性
- 验证状态
- 阻塞点清晰度
- 风险变化
- 继续准备度

### 评审原则

Claude Code 应产出可评审的开发输出。

它不应要求 Xuanzhi 从原始混乱中重建整个上下文。

---

## 失败与恢复姿态

Claude Code 是受控恢复模型的一部分。

### 步骤或任务失败

如果执行在限定级别失败，默认的下一步操作通常是：

- 如果路径仍然合理且在重试边界内，则重试
- 否则重规划

### 里程碑失败

默认下一步操作：

- 重规划里程碑

里程碑失败不自动意味着整个项目失败。

### 重复失败

当有限次数的重试耗尽时，正常的下一步操作不是盲目坚持。

正常的下一步操作是：

- 重规划
- 或者如果路径风险太高或太不清晰，则升级

### 原则

预期 Claude Code 清晰地暴露失败，而非将其隐藏在叙事性的乐观中。

---

## 长周期开发窗口

长周期开发应被视为限定范围的活跃窗口，而非无尽的不间断流。

默认活跃窗口：

`24 小时`

在长活跃窗口后，系统应预期：

- 检查点或提交
- 进度汇总
- 阻塞状态
- 继续决策

Claude Code 不需要在边界处精确停止现有工作，
但治理模型预期周期性的可评审检查点。

---

## 汇报期望

Claude Code 应以支持 Xuanzhi 汇报角色的结构返回结果。

至少，汇报应能够保留：

- 任务摘要
- 状态摘要
- 变更的文件或产物引用
- 运行的测试/检查
- 阻塞点
- 有用时的后续步骤建议

### 汇报原则

优先：

- 简洁的摘要
- 产物引用
- 简洁的备注

避免：

- 冗长的原始记录
- 未过滤的实现闲谈
- 冗长的自我辩护堆砌

---

## 分支与合并姿态

Claude Code 应在分支感知的开发流程中操作。

默认受治理路径保持：

议题 -> 分支 -> 合并请求 -> CI -> 评审 -> 合并

### 分支期望

当分支策略适用时，Claude Code 应遵循相关的分支族并在分支范围内工作，而非随意修改共享面。

### 合并原则

Claude Code 可以为合并准备工作，
但合并仍受 CI、评审和审批姿态（在适用时）的治理。

---

## 测试与验证姿态

Claude Code 应在验证相关且可行时验证开发输出。

典型的验证期望包括：

- 测试
- 代码检查
- 构建检查
- 限定范围的验证命令
- 当验证无法完成时的明确说明

### 原则

没有验证信号的开发结果弱于有明确验证姿态的结果。

如果未运行验证，应清晰说明，而非暗示忽略。

---

## Claude Code 内部的团队协作

当内部任务分解或开发团队风格的协调能改善执行时，可以在 Claude Code 内部进行。

这是可接受的，只要：

- Xuanzhi 保持治理控制平面地位
- Claude Code 保持在受控的执行范围内
- 输出保持结构化且可评审
- 权限不静默扩展
- 追踪和汇总质量保持充分

### 原则

内部协调是执行质量的工具，
而非将治理向上或向侧面移动的借口。

---

## 风险与审批交互

Claude Code 执行不绕过风险或审批姿态。

如果委托的任务涉及：

- 升高的风险
- 破坏性潜力
- 权限敏感的后果
- 合并或激活关卡
- 结构上重要的变更

则执行仍应遵循相关的评审、审批或升级路径。

### 原则

执行器能力不是许可。

---

## 仓库本地治理感知

当仓库在 `/.governance` 下包含项目本地治理时，
Claude Code 应将其视为仓库本地的操作上下文，而非全局工作空间策略。

### 层级区分

- 工作空间级治理 -> 主 Xuanzhi 工作空间
- 仓库本地治理 -> 目标仓库

Claude Code 不应在没有明确任务契合和许可的情况下静默重写治理层。

---

## 集成边界

本文档有意不定义：

- 完整的 Claude Code 提示词内容
- 完整的 Claude Code 安装过程
- 所有 Claude Code 命令或标志
- 低级运行时容器细节
- 控制器实现代码
- GitLab API 细节

这些属于：

- 产品文档
- 运维手册
- GitLab 集成规范
- 实现级的设置或部署文档

本文档只有保持聚焦于执行姿态才能保持有用。

## 本规范应防止的失败模式

本规范的存在部分是为了防止：

- 顶层执行过载
- 没有治理框架的仓库本地开发
- 没有检查点的长周期开发
- 太嘈杂而无法评审的开发输出
- 没有受控恢复的重复失败
- 无分支或无视结构的执行漂移
- 执行器能力被误认为审批权限

---

## 最终原则

Claude Code 应承担繁重的开发工作，而非治理负担。

正确的集成使 Xuanzhi 保持控制，使 Claude Code 保持有效，使长周期开发保持可读、有检查点且可评审。
